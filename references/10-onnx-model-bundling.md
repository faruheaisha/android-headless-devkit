# 端侧大模型打包与推理集成（ONNX 为例）

> 场景：把一个上百 MB 的推理模型（TTS / OCR / ASR / 分类器）**打进 APK**，
> 在中低端手机上离线跑。本文的数字全部来自一次真实集成
> （109MB fp32 ONNX 语音合成模型，VITS 架构，x86_64 无头模拟器实测）。
> 关联：资产许可与"黄金夹具"见 [08](08-dependency-and-environment-baseline.md) §3；
> R8 keep 规则见 [04](04-dependency-versions.md) §6；真机/模拟器差异见 [09](09-real-device-verification.md)。

---

## 1. 分发方式决策：打包 / 首用下载 / 量化

| 方式 | 适合 | 代价 |
|---|---|---|
| **打包进 APK** | 接收方是直接拿 APK 的家人/客户；要"开箱即用、离线可用" | 包体 +模型大小；应用商店有单包上限（Play AAB 可绕，国内渠道见各自限制） |
| 首用下载 | 走应用商店、包体敏感 | 首用失败率高（弱网/权限），必须做断点与校验 |
| 量化（fp32→int8） | 极度在意包体与内存 | **先验证再决定**：某些模型/运行时组合量化后质量不可用，或 CPU 算子不支持 |

实测教训（决策前先跑，别信默认直觉）：

- **用户母语听感验收**后选择了"打包 fp32 不量化"——音质是产品要求，
  包体从 24MB 涨到 150MB 是**被接受的代价**。量化与否是产品决策，不是技术炫技。
- **静态量化在 ORT CPU 上未必可行**：校准器对动态 shape 的子图直接崩
  （同一个输入 fp32 推理完全正常），换 `nodes_to_exclude` 也绕不开——
  校准器插桩的是整张图。遇到时先确认是不是这个坑，别在错误层面对症。

## 2. 资产打包：三件必须做对的事

### 2.1 大模型资产标记 `noCompress`

```kotlin
androidResources {
    noCompress += "onnx"   // 扩展名，不含点
}
```

为什么：

- 权重是近乎随机的 float32，deflate 收益很小（实测省不出 10%）；
- 不压缩时 APK 里的条目是 **STORED**，首用拷贝是**纯文件复制**——
  没有解压的 CPU 与内存尖峰（低端机解压 109MB 是能感知的卡顿）；
- 核验方式（打包后必须做）：

```python
import zipfile, hashlib
z = zipfile.ZipFile("app-release.apk")
info = z.getinfo("assets/model.onnx")
assert info.compress_type == 0                      # STORED
assert info.file_size == 本地源文件字节数
assert hashlib.md5(z.read(...)).hexdigest() == 本地md5  # 内容一致
```

### 2.2 首用拷贝到应用私有目录，而不是每次读 assets

assets 的 `InputStream` **无法 mmap**，直接读只能整块进内存。
正确做法：首次使用把资产拷到 `filesDir`（流式 64KB 缓冲 + `fd.sync()` +
临时文件 rename），之后用文件路径加载。三个细节：

1. **用文件大小做一致性校验**——APK 升级换了模型时自动重新拷贝；
2. 临时文件写完再 rename（半截文件会被当成可用模型）；
3. 拷贝耗时要在日志里报出来（实测 109MB 冷启 6.4s / 页缓存热 1.8s）——
   它是"第一次特别慢"的一部分，必须能让验收者知道这是一次性的。

### 2.3 会话用**路径**加载，不用 `byte[]`

```kotlin
// 好：ORT 对路径加载可 mmap，权重不额外复制进 Java 堆
val session = env.createSession(modelFile.absolutePath, options)
// 坏：readBytes() 会把 109MB 再复制一份进堆 —— 低端机 OOM 风险
val session = env.createSession(context.assets.open("m.onnx").readBytes(), options)
```

会话是昂贵的：**懒加载一次 + 全局复用**（`synchronized` 单例），
不要每次播放/推理都建。

## 3. 会话参数 A/B：图优化是"创建成本"，不是"推理收益"

**这是本文最值钱的一条。** 默认 `OptLevel.ALL_OPT` 在 109MB VITS 上，
会话创建（图优化）要 **31.6 秒**——用户第一次点朗读要干等半分钟。
同一设备、同一句输入的 A/B：

| 配置 | 会话创建 | 首句推理 | 稳态推理 |
|---|---|---|---|
| `ALL_OPT` + 2 线程 | 31,648 ms | 43,111 ms | — |
| **`BASIC_OPT` + 4 线程** | **5,704 ms** | **8,143 ms** | **4,097 ms/句** |

结论与方法论：

- **把"加载慢"和"推理慢"分开测量**（各自打一行日志，见 [09] §3.2 三连证据），
  否则你根本不知道该优化哪头；
- 大模型上 ALL_OPT 的图变换本身是分钟级开销、推理收益很小 → 取 `BASIC_OPT`；
- 线程数给到 4（8 核手机），别用默认单线程，也别占满 8 核饿死 UI；
- A/B 必须在**同一设备、同一输入**上跑，两个数字都要报。

## 4. 文本前端：与官方分词器**逐 id 对拍**

端到端模型喂的是 id 序列，分词错一个 id，音频/输出就错，而且**听起来"差不多对"**，
极难排查。铁律：**直觉规则不叫验证，逐 id 相等才叫。**

一个真实案例（教训浓缩）：

- 模型的 HF 分词器把某字母（恰是词表 id 0、同时是 pad）注册为 **special token**，
  分词时**按它切段**、每段独立插 pad；
- 于是"每个字符 [pad,id] 插空、末尾补 pad"这个**直觉规则在多数句子上恰好全对**，
  但**句首/句尾恰好是该字符时会少一个 pad**——而这个词尾在目标语言里极常见；
- 用黄金夹具对拍后才暴露：3 句常规样本全 MATCH，加上边界用例立刻 DIFF。

边界用例必须覆盖：**句首/句尾是 special token、连续 special token、
词表外字符（标点/未收录数字/外语）、首尾空白、纯 OOV 空串**。
对拍基准是官方分词器本身，不是自己的移植实现（否则是用错误验证错误）。

配套工程（见 [08] §3）：夹具（输入 → 期望 ids）**入库**，单测**直接读随包资产**断言
——词表或夹具被误改，测试立刻红。上游分词库**锁版本**（它的行为就是模型语义的一部分）。

## 5. 组合验证：release 包在模拟器上装不了怎么办

release 只打 arm64（省体积），**x86_64 模拟器装不了它**
（`INSTALL_FAILED_NO_MATCHING_ABIS`）→ release 的运行时行为没法在模拟器上看。
可行且已验证的组合：

1. **同配置 debug 包做"运行时可见验证"**：把 release 的关键构建开关
   （功能入口开关、地址配置）在 debug 上设成**完全相同**的值，构建 debug 装进
   模拟器，实拍可见行为（入口隐藏、页面状态）；
2. **release 做静态核对**（每项都可脚本化）：
   - 生成的 `BuildConfig.java`（`app/build/generated/source/buildConfig/<variant>/`）
     逐字段核对开关值；
   - `apksigner verify --print-certs` 签名与签名者；
   - zipinfo/zipfile 核对大资产 `STORED` + md5 与源一致；
   - 解包 `classes.dex` 搜推理引擎类名（如 `ai/onnxruntime/OrtSession`）确认
     keep 规则生效、未被 R8 裁掉；
3. **剩余风险如实写**：R8 相关的运行期问题，最终仍需 arm64 真机确认
   （[09] 的"不可外推"原则在这里同样成立）。

> debug 构建不跑 R8 —— **keep 规则写错，debug 全绿也证明不了 release 没事**。

## 6. 首次体验：把"慢"变成"可见的等待"

首次使用 = 拷贝（秒级）+ 会话创建（秒级到十秒级）+ 首次推理。三段都要：

- **状态可见**：`isPreparing`（合成/加载中，按钮转圈）与 `isPlaying` 分开；
- **可取消**：等待中点击 = 取消（比"点了没反应"强一个量级）；
- **日志三连**（[09] §3.2）：`资产拷贝完成 N bytes 耗时=Xms` →
  `模型加载耗时=Yms` → `合成完成 samples=Z 耗时=Wms`。

实测（BASIC_OPT 配置，模拟器）：拷贝 1.8s → 加载 5.7s → 首句 8.1s，
第二句起 4.1s/句。**首次慢是结构性的、一次性的**——写进文档，
验收者才不会把它当性能缺陷；要更快，方向是预加载（进页面即后台建会话），
不是调优化级别。

## 7. 检查清单

- [ ] 量化与否做过**质量验收**（听感/目测），不是只看体积数字
- [ ] 大资产已 `noCompress`；包内核对 `STORED` + md5 与源一致
- [ ] 首用拷贝：流式写入、临时文件 rename、**文件大小校验**支持升级自动重拷
- [ ] 会话用**路径**加载；懒加载单例复用；"加载耗时"与"推理耗时"分开打日志
- [ ] 会话优化级别做过**同机同输入 A/B**（默认值不一定适合大模型）
- [ ] 分词/前处理与官方实现**逐 id 对拍**；夹具含 special token 边界用例；上游库锁版本
- [ ] R8：JNI/反射引擎包名有 `-keep`（[04] §6）；**debug 不跑 R8**，
      release 至少做一次静态核对（dex 类名存在 + BuildConfig 字段 + 签名）
- [ ] release 与 debug 的 ABI 差异已知悉；模拟器验证用**同配置 debug 包**替代
- [ ] 首次等待有状态、可取消；"首次慢是一次性的"写进了项目文档
- [ ] 模拟器数字标注**不可外推**，真机听感/时延单列待办
