# 物理真机验证工作流

[03](03-device-verification.md) 讲的是**无头模拟器**上的自动化验收 ——
快、可重复、适合每轮改完就跑。

这一篇讲**物理真机**。两者不是替代关系：

| | 无头模拟器 | 物理真机 |
|---|---|---|
| 适合 | 每轮改动的渲染/布局/链路回归 | 交付前终验、性能与听感、真实权限与厂商行为 |
| 优势 | 可脚本化、可反复跑、环境可控 | 真实硬件、真实网络、真实手感与观感 |
| 短板 | 无摄像头、无语音包、软件渲染慢 | 需人工介入、状态难复现 |
| 结论能否互推 | ❌ **不能** | ❌ **不能** |

> ★ **最重要的一条**：**模拟器的数字不能外推到真机**。
> 模拟器是纯软件执行（无硬件加速），时延往往比真机慢数倍；
> 反过来，"模拟器上正常"也不能证明"真机上正常"——
> 厂商 ROM 的权限策略、后台限制、厂商定制行为都只在真机上出现。
> 报告里必须写清结论来自哪一类设备。

## 1. 手机一次性准备

1. 设置 → 关于手机 → 连点「版本号」7 次，开启**开发者选项**；
2. 开发者选项里打开 **USB 调试**（Android 11+ 也可用**无线调试**配对，免线更方便）；
3. USB 连接电脑，手机弹「允许 USB 调试吗」→ 允许（可勾选"一律允许"）；
4. 验证：

```bash
adb devices
```

| 输出状态 | 含义 | 处置 |
|---|---|---|
| `device` | ✅ 就绪 | 继续 |
| `unauthorized` | 手机上还没点"允许" | 在手机上确认；必要时撤销授权重来 |
| 无设备 | 线/驱动/调试开关 | 换线（**充电线常常没有数据能力**）、确认调试开关 |

## 2. 构建与安装

```bash
# 构建（环境变量见 08 §1）
gradle -p <短路径> :app:assembleDebug      # 调试包（含 x86_64，可装模拟器）
gradle -p <短路径> :app:assembleRelease    # 交付包（仅 arm64）

# 安装
adb install -r -t <debug.apk>      # -r 覆盖；-t 允许测试包
adb install -r   <release.apk>

# 启动
adb shell am start -n <包名>/<主 Activity>

# 卸载（换签名、清干净状态时用）
adb uninstall <包名>
```

### ★ 装机失败的三个高频原因（都要先分清再动手）

| 报错 | 根因 | 处置 |
|---|---|---|
| `INSTALL_FAILED_UPDATE_INCOMPATIBLE` | **debug 与 release 签名不同**，覆盖安装被拒 | `adb uninstall <包名>` 后重装。调试签名与本地测试签名天然不是同一个 |
| `INSTALL_FAILED_NO_MATCHING_ABIS` | 包里没有该设备的 `.so` 架构 | 真机用 arm64；**x86_64 模拟器装不了只带 arm64 的 release 包** |
| `INSTALL_FAILED_VERSION_DOWNGRADE` | 装的版本号比已装的低 | 卸载重装，或提高 `versionCode` |

> **debug 与 release 不能互相覆盖**这件事要在流程上预防：
> 交付前终验要清数据，用 `adb uninstall` 彻底清干净再装 release，
> 否则会残留 debug 期的数据（缓存、授权状态），让终验结果失真。

## 3. 用 logcat「看见」App —— 人和 Agent 通用的验收方式

截图能看「界面画对了没有」，logcat 能看「内部真的走到哪一步了」。
两者合起来才构成一次完整验收（理由见 [03](03-device-verification.md) §9）。

### 3.1 关键设计：给日志加**统一前缀 + 模块 tag**

这是个一次投入长期受益的约定：

```
<统一前缀>:<模块>   例如  UT:Network / UT:Tts / UT:Ocr / UT:DocJob
```

好处：

- **可精确过滤**，在几千行系统日志里一句话捞出自己关心的
- **前缀使"漏加日志"变得显眼** —— 名字不统一，一眼就能看出
- 验收脚本可以据此断言，不必依赖界面文案（文案会变、会被本地化）

**注意**：不要把密钥、用户内容写进日志。日志会被用户导出反馈问题。

### 3.2 长链路的「三连证据」

对于多阶段的链路（加载模型 → 处理 → 输出），
只打一行"成功了"是不够的 —— 出问题时无法定位卡在哪一段。
**每段各打一行，形成可断言的序列**：

```
① 准备完成（若涉及首次拷贝/解压，报出耗时与字节数）
② 资源加载完成（报出耗时）
③ 任务完成（报出关键量纲与耗时）
```

三行齐了就是端到端 OK；缺哪一行就卡在那一段。这比"报个成功/失败"信息量大得多。

实测有的链路里，**首次运行特别慢是正常的**（一次性的拷贝或加载），
这一点要写进文档，否则会被当成性能缺陷。

### 3.3 常用过滤命令

```bash
adb logcat -v time | grep "UT:Network"          # 网络链路
adb logcat -v time | grep "UT:Tts"              # 语音合成链路
adb logcat -v time | grep "UT:DocJob"           # 长任务（进度/续跑）
adb logcat -b crash                             # 只看崩溃缓冲区
adb logcat -v brief | grep -c "FATAL EXCEPTION" # 崩溃计数（应为 0）
```

> 崩溃判据用 **`FATAL EXCEPTION`**，不要用应用名模糊匹配 ——
> 崩溃缓冲区里系统组件的 ANR 记录会提到前台应用名，会造成误报。
> 详见 [03](03-device-verification.md) §4。

## 4. 调试路由：把"点若干次才能到"变成"一句话直达"

延续 [03](03-device-verification.md) §5.3 的思路：给 App 一个**仅 debug 生效**的入口，
用 `am start --es <key> <value>` 直达任意页面并预置输入。

```bash
# 直达某页
adb shell am start -n <包名>/<Activity> --es route <页面键>

# 直达 + 预置非 ASCII 文本（b64 前缀，避免 shell 编码问题）
adb shell am start -n <包名>/<Activity> --es route <页面键> --es input "b64:<base64>"
```

典型路由表（按自己应用的实际页面填）：

| 键 | 页面 | 键 | 页面 |
|---|---|---|---|
| `home` | 首页 | `result` | 结果页（预置内容，便于核对排版） |
| `text` | 文本输入 | `history` / `settings` | 历史 / 设置 |
| `camera` / `gallery` / `crop` | 拍照链路各阶段 | `licenses` | 开源许可 |

**三条纪律**：

1. **必须门控**（`BuildConfig.DEBUG` 或一个 debug-only 的开关）。
   **release 包必须关闭该入口** —— 否则等于给生产包留了一条外部可注入参数的通道。
   验证方式：release 包执行同一命令，应回落到默认页。
2. **参数注入到输入框，不要自动发起请求**。自动发起会掩盖"按钮是否可点、
   是否该置灰、失败文案对不对"这些本来要验的东西。
3. **值用 `b64:` 前缀传非 ASCII**。`adb shell input text` 只支持 ASCII，
   这是硬限制（见 [03](03-device-verification.md) §5.3）。

## 5. 回归验证清单（模板）

每轮真机验证照着走。**表格骨架固定，内容按自己的业务填** ——
固定骨架的价值是"每次都覆盖同样的东西"，不会因为赶时间就漏掉某条链路。

| # | 验证项 | 通过标准（要可判定，不能写"正常"） |
|---|---|---|
| 1 | 主链路 A（如：文本翻译） | 出结果；**日志有请求记录**；断网时出友好提示且**不崩溃** |
| 2 | 主链路 B（如：图片 → 处理） | 各阶段可进可退；中间态有可见反馈 |
| 3 | 长任务（如：文档分块处理） | 有进度；**杀进程重开可续**（日志显示状态迁移） |
| 4 | 语音/输出类 | 有对应日志三连 + 实际能听到/看到；进行中可取消 |
| 5 | 本地持久化 | 杀进程重开仍在；设置项持久化生效 |
| 6 | 交付包专属差异 | 应当隐藏的入口确实隐藏；**不存在假开关**（点了没反应的开关比没有开关更糟） |

**构建期回归**（每次改代码后，比真机更快）：

```bash
gradle -p <短路径> test          # 全量 JVM 测试
gradle -p <短路径> :app:assembleDebug :app:assembleRelease   # 两个包都能出
```

> 记录**基线数字**（如"166 个测试 / 0 失败"）。
> 有了基线，"这轮改动有没有打破什么"就变成一个可对比的事实，而不是感觉。

## 6. debug / release / benchmark：三种包的差异必须清楚

| 维度 | debug | release（交付包） | benchmark |
|---|---|---|---|
| ABI | arm64 + x86_64 | **仅 arm64** | arm64 + x86_64 |
| 混淆（R8） | 关 | **开** | 开但保留可调试（供剖析） |
| 调试路由 | 开 | **关** | 开 |
| 地址放行 | 可放宽（含本机回环） | **只接受 HTTPS** | 同 debug |
| 可选功能入口 | 可开 | 按交付配置 | 按配置 |

**由此推出的实操结论（都真实踩过）**：

- **真机联调时 `http://` 一律不行**（release 只认 https）→
  要么部署 HTTPS 服务，要么在模拟器上联调；
- **x86_64 模拟器装不了 release 包** → 模拟器验收一律用 debug 包；
- **模拟器报语音合成失败（负状态码）≠ App 缺陷** →
  通常是模拟器没装该语言的系统语音包。要把它写进"已知环境限制"，
  否则每一轮都会有人重新排查一遍。

> 把这张表放进项目文档。它是"为什么同样的操作在两种包上结果不同"的答案，
> 而这个问题在交付前必然会遇到。

## 7. 报告时的纪律

- **写清结论来自哪类设备**（模拟器 / 哪款真机、系统版本）。
  模拟器的时延数字**标注为不可外推**。
- **区分已验证与未验证**。真机终验往往依赖外部条件
  （服务端部署、密钥轮换），这些没做完就**不要写"已可交付"**。
- **未完成的门要单独列出**，并写清"做完它才能叫交付"。含糊过去，
  最后会在最不方便的时候暴露。

## 8. 一句话检查清单

- [ ] `adb devices` 状态为 `device`
- [ ] 换包装不上时，先判是不是**签名冲突**（debug ↔ release 不能互相覆盖）
- [ ] 交付前 `adb uninstall` 清干净，再装 release（避免 debug 残留数据污染终验）
- [ ] 日志有统一前缀 + 模块 tag，长链路有**三连证据**
- [ ] 崩溃判据用 `FATAL EXCEPTION`，不用应用名
- [ ] 调试路由存在、可预置输入，且 **release 已关闭**
- [ ] 回归清单逐条走过，**通过标准是可判定的**
- [ ] 记录构建期回归的基线数字（N 个测试 / 0 失败）
- [ ] 清楚 debug/release/benchmark 三类包的差异，并知道由此产生的限制
- [ ] 报告写清设备类型；模拟器数字标注**不可外推**
- [ ] 未完成的门单独列出，不写"已可交付"
