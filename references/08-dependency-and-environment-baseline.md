# 环境与依赖基线

**目标**：换一台电脑、换一个人、换一部手机，都能照着复现出同一个可构建、可安装、可验收的环境。

写这份东西的原因很直接：环境问题最耗时，而它**不写在代码里**。
一个人调通之后不落纸，下一个人（或半年后的自己）会重踩一遍，
而且症状往往指向错误的方向（报"目录不存在""缺少类""空间不足"，其实是另一回事）。

组织方式：**只写已验证的取值，未验证的明确标注**。

---

## 1. 环境变量与参数

命令行构建前必须设置（写进脚本，别靠记忆）：

```bash
JAVA_HOME         = <DevRoot>/jdk-17
ANDROID_HOME      = <DevRoot>/sdk
ANDROID_SDK_ROOT  = <DevRoot>/sdk      # 有些工具只认这个，两个都设最省事
ANDROID_AVD_HOME  = <DevRoot>/avd
GRADLE_USER_HOME  = <DevRoot>/gradle-home
```

> `DevRoot` 是本 skill 的默认值概念：默认 `E:\AndroidDev`，由 `scripts/env.ps1 -DevRoot` 覆写。
> **凡是可配置的地方都要说清它是参数**，不要把某一台机器的布局写死在正文里。

**两个必做动作**：

```bash
# ① 清空失效代理。历史上配过一次性会话代理（如 127.0.0.1:xxxxx），
#    进程没了但环境变量还在 → Gradle 连不上任何源，且报错不指向代理。
export HTTP_PROXY="" HTTPS_PROXY="" http_proxy="" https_proxy=""

# ② 先体检再干活，别等构建失败才发现环境不全
ls "$JAVA_HOME/bin/java.exe" "$ANDROID_HOME/platform-tools/adb.exe" "$GRADLE_BIN"
```

## 2. 依赖盘点：怎么记，以及为什么必须记许可

### 2.1 单一真相来源

依赖版本只允许有一个出处（Gradle 版本目录 `gradle/libs.versions.toml`）。
散落在各模块 `build.gradle.kts` 里的硬编码版本，迟早会出现"两个模块用不同版本"的
诡异现象，而且排查时不知道以哪个为准。

### 2.2 盘点表要按**用途**分组，不是按字母序

按用途分组才能回答"我要换掉某个能力时，动哪几个依赖"：

| 用途 | 依赖 | 版本 | 许可 |
|---|---|---|---|
| 构建 | AGP / Kotlin / KSP | … | Apache-2.0 |
| UI | Compose BOM / Material3 | … | Apache-2.0 |
| 导航 | navigation-compose | … | Apache-2.0 |
| 数据库 | Room | … | Apache-2.0 |
| 注入 | Hilt | … | Apache-2.0 |
| 网络 | OkHttp / kotlinx-serialization / coroutines | … | Apache-2.0 |
| 图片 | Coil / 图片裁剪 / 玻璃质感库 | … | Apache-2.0 |
| 端侧推理 | onnxruntime-android 等 | … | MIT |
| 文档解析 | PDF/Office 解析库 | … | Apache-2.0 |

**版本列必须来自实际生效的值**，不要照抄官方文档的推荐版本 ——
传递依赖会把版本线整体抬高（见 [04](04-dependency-versions.md)）。

### 2.3 许可：一条红线 + 一次核对

**红线**：代码依赖限 **MIT / Apache-2.0 / BSD**，不含 GPL / AGPL / LGPL。

**核对方法**（不要靠记忆，要扫）：

1. 解析全部依赖制品，导出「制品 → 许可」清单；
2. 生成随包声明文件（把清单固化进 `assets/` 之类的位置，随包分发）；
3. 对无法自动判定的制品**逐个人工确认**，并在表里标注"已解析数量"。

> **实测教训**：**随包模型资产常常不在代码依赖的许可体系里**。
> 代码侧全部干净，但随包的模型权重可能是 **CC-BY-NC（非商业）** 之类的限制性许可。
> 这类资产必须单独列表、单独声明，并且在"将来若商业化"时列出替换动作。
> 把它混在代码依赖里一起说"全部 MIT/Apache"是不准确的。

## 3. 大文件资产：不入库，但要可复现

模型权重、大词表之类动辄上百 MB 的资产，**不进版本库**（`.gitignore`），
但这带来一个必踩的坑：**别人克隆之后能构建成功，运行时才报资产缺失**。

**通用模式：入库"可复现的三件套"，不入库大文件。**

| 资产类型 | 入库？ | 作用 |
|---|---|---|
| 大权重文件（数十至数百 MB） | ❌ gitignored | 体积太大 |
| 导出脚本 | ✅ | 从上游重新生成权重，一条命令 |
| 词表/配置（KB 级） | ✅ | 运行时必需，体积小 |
| **黄金夹具**（golden fixture） | ✅ | 断言生成结果正确，见下 |

### 3.1 为什么必须有"黄金夹具"

同一份权重，用不同的上游库版本导出，**结果可能不同**（分词行为、算子融合都会变）。
只验证"文件存在"是不够的 —— 文件可能是坏的对齐。

做法：挑少量代表性输入（若干正常句 + 一批边界用例），
把上游官方实现的输出**逐项固化**成夹具文件随包入库，
单测里断言本地实现的输出与夹具**逐 id 相等**。

价值：上游库升级时（例如把 `transformers` 换大版本），
**不一致会立刻在单测暴露**，而不是等到线上出现诡异的输出偏差。

```bash
# 克隆后必做一步（否则能构建、运行时才炸）
<安装上游依赖>
python tools/export_<资产名>.py
# 校验：跑该模块的单测，夹具会逐项断言
gradle -p <短路径> :<模块>:test
```

> **要把这一步写进 README 的"快速开始"**，不能只在 reference 里提一句。
> 因为它的失败时机很晚（运行时），不提前做会浪费大量排查时间。

## 4. 密钥：永远不进 APK

**基线**：打包进 APK 的任何长期密钥，都应视为**已泄露**（APK 可被反编译）。
仅删除代码里的引用**不能**让已泄露的密钥失效 —— 必须**轮换密钥本身**。

### 4.1 分层模式

| 层 | 放什么 | 不放什么 |
|---|---|---|
| 客户端（APK） | 端点地址（`https://...`） | 任何供应商密钥 |
| 本机/服务端代理 | 供应商密钥（**只在这里**，来自环境变量或本机配置） | — |

客户端只认代理地址，代理负责持密钥、固定上游模型、限流、日预算熔断、
**不记录内容日志**（用户文本可能含隐私）。

### 4.2 怎么验"APK 里真的没有密钥"

不要靠"我改过代码了"。**扫产物**：

```bash
# ① 反编译 DEX 后搜密钥特征
#    判据：长密钥模式 0 处 + 不存在那个密钥字段名
# ② 确认相关 BuildConfig 字段在 release 里为空或不存在
```

本项目实测判据：`sk-...` 长密钥 **0 处**，且不含任何供应商密钥字段名。

### 4.3 调试期密钥的注入方式

开发期需要一个不进版本库的注入通道。常见做法是 `local.properties`（已被 gitignore）
→ Gradle `buildConfigField` → `BuildConfig`：

```properties
# local.properties（不进版本库）
<provider>.apiKey=...
<provider>.baseUrl=https://.../v1     # 注意只写到 /v1，客户端会自己拼路径
<provider>.model=...
```

**三条容易错的细节**：

1. **baseUrl 只写到版本段**（`/v1`）。客户端拼 `${baseUrl}/chat/completions`，
   把完整 URL 填进去会变成 `.../chat/completions/chat/completions`。
2. **模型名做成配置项**。服务商改模型名是常态，写死意味着每次都要重新编译。
3. **debug 与 release 的放行策略要不同**。典型：
   debug 放行本机回环地址（模拟器用 `10.0.2.2`），
   release **只接受 `https://`**。这样能把"联调用的不安全配置"挡在交付包之外。

## 5. 设备与运行时要求（写进项目文档，别只留在脑子里）

| 项 | 要定的事 | 为什么要写 |
|---|---|---|
| Android 版本 | `minSdk` / `targetSdk` | 决定可测设备范围 |
| CPU 架构 | release 只留 `arm64-v8a`；debug 加 `x86_64` | debug 带 x86_64 是为了模拟器；release 省体积 |
| 存储 | 首次运行是否需要额外空间（解压/拷贝随包资产） | 用户会以为"装完就能用" |
| 权限 | 哪些是必需的，哪些可免 | **走系统选择器（相册/文件）是免权限的**，比申请权限更好 |
| 系统能力依赖 | 是否需要系统语音包 / Play 服务 / 在线下载 | 缺失时的现象要写清，否则会被当成 App 缺陷 |

> **"免权限"是设计资产**：能走系统选择器拿文件，就不要申请存储权限。
> 少一个权限就少一类拒绝路径，也少一段解释成本。

## 6. 磁盘与内存预算（构建期）

**内存**：构建需 **≥2.5GB 可用内存**（提交内存，不是物理内存）。
云盘客户端是常见元凶 —— 实测单个云盘进程可提交十几 GB，
导致 Gradle JVM 原生内存崩溃（留下 `hs_err_pid*.log`）。
**构建前先退出云盘客户端。**

**磁盘**：

| 项 | 量级 | 说明 |
|---|---|---|
| 构建中间产物峰值 | ~2GB | 每模块 `build/` 累积 |
| 依赖缓存（`GRADLE_USER_HOME`） | 数 GB | **`caches/modules-2` 不许删**（是依赖仓库不是缓存，见 [01](01-environment-setup.md) §5.2） |
| AVD 数据分区 | 默认 ~7GB | 空间紧张时把 AVD 挪到大容量盘（改 `AVD_HOME` 并同步 `.ini` 里的 `path`） |
| 随包大资产 | 视模型而定 | 会同时体现在仓库外与 APK 体积上 |
